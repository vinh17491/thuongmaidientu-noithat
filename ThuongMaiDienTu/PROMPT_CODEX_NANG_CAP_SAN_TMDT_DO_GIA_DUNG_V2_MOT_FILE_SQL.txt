## 2. Chiến lược database — RÀNG BUỘC CỨNG: CHỈ MỘT FILE SQL

Repo hiện dùng SQL Server và có file SQL hiện hữu của dự án. Toàn bộ thay đổi database phải được quản lý trong **một file SQL duy nhất**.

### 2.1 File SQL duy nhất được phép chỉnh sửa

- File mục tiêu là file SQL hiện có tên `thuongmaidientu.sql`.
- Nếu file trong workspace đang có tên chính xác là `thuongmaidientu(1).sql`, phải dùng chính file đó làm file mục tiêu.
- Không tự đổi tên nếu việc đổi tên có thể tạo thêm bản sao.
- Trước khi sửa, dùng tìm kiếm trong repository để xác định đúng file SQL hiện hữu.
- Sau khi xác định, ghi rõ đường dẫn file mục tiêu trong audit.
- Chỉ được sửa nội dung trong file SQL mục tiêu đó đối với mọi thay đổi DDL, DML, seed và verification.

### 2.2 Nghiêm cấm tạo thêm SQL hoặc migration

Không được:

- Tạo thư mục `database/`, `sql/`, `scripts/database/` hoặc thư mục tương tự chỉ để chứa thêm SQL.
- Tạo bất kỳ file `.sql` mới nào như:
  - `schema.sql`
  - `migration.sql`
  - `upgrade.sql`
  - `seed.sql`
  - `verification.sql`
  - `rollback.sql`
  - `001_*.sql`, `010_*.sql`, `020_*.sql`
- Chạy `dotnet ef migrations add`.
- Tạo thêm thư mục hoặc class EF Migration.
- Generate migration script sang một file SQL khác.
- Sao chép file SQL mục tiêu thành bản `new`, `final`, `v2`, `backup`, `fixed` hoặc tên tương tự trong repository.
- Đưa SQL rải rác vào README, controller hoặc source code để thay cho file SQL chính.

Các EF Migration cũ đang tồn tại trong repo, nếu có, chỉ được giữ nguyên để tránh phá project. Không thêm migration mới.

### 2.3 Cấu trúc bắt buộc bên trong một file SQL

Sắp xếp `thuongmaidientu.sql` thành các section rõ ràng trong cùng một file:

1. Header:
   - Mục đích file.
   - Database name: `thuongmaidientu`.
   - Ngày cập nhật.
   - Cảnh báo backup.
   - Hướng dẫn chạy.
2. Tạo database nếu chưa tồn tại và `USE thuongmaidientu`.
3. Nâng cấp schema an toàn:
   - Tạo bảng nếu chưa tồn tại.
   - Thêm cột nếu chưa tồn tại.
   - Backfill dữ liệu.
   - Thêm default/check/foreign key sau khi dữ liệu hợp lệ.
4. Constraints và indexes.
5. Views, procedures hoặc functions.
6. Seed/demo data có `IF NOT EXISTS`.
7. Verification queries ở cuối file.
8. Chú thích rõ các thay đổi marketplace.

Dùng comment section lớn để file dài vẫn dễ quản lý.

### 2.4 Yêu cầu an toàn và chạy lại được

- File phải idempotent ở mức hợp lý và có thể chạy lại mà không tạo duplicate data.
- Không mặc định `DROP DATABASE`.
- Không mặc định xóa toàn bộ bảng hoặc dữ liệu.
- Phải loại bỏ/refactor khối đang `DROP TABLE` hàng loạt nếu nó gây mất dữ liệu.
- Chỉ được `DROP/CREATE` view hoặc procedure khi không làm mất dữ liệu nghiệp vụ.
- Với thay đổi bảng:
  1. Kiểm tra tồn tại.
  2. Thêm cột nullable nếu cần.
  3. Backfill.
  4. Kiểm tra dữ liệu lỗi.
  5. Mới thêm constraint hoặc chuyển sang `NOT NULL`.
- Dùng transaction cho từng nhóm nâng cấp có thể rollback an toàn.
- Dùng `TRY...CATCH`, `XACT_STATE()` và `THROW` cho các block thay đổi quan trọng.
- Không nuốt lỗi.
- Không dùng `EnsureCreated`.
- Không xóa dữ liệu cũ chỉ để làm schema mới dễ hơn.
- Trước khi chạy trên database hiện có, phải tạo backup.
- Rollback dựa trên database backup; không tạo file rollback SQL riêng.

### 2.5 Đồng bộ EF Core

### 3.4 Giỏ hàng và checkout đa cửa hàng

Giỏ hàng phải:

- Chứa sản phẩm từ nhiều store.
- UI group theo từng cửa hàng.
- Cho chọn đúng SKU/variant.
- Hiển thị tổng tiền từng store và tổng toàn giỏ.
- Kiểm tra lại status, giá và stock ở server.
- Không tin giá gửi từ client.
- Không cho thêm sản phẩm của store/product/SKU bị khóa.

Checkout phải:

1. Group cart item theo `StoreId`.
2. Tạo một `orders` cha cho customer.
3. Tạo một `store_orders` cho từng store.
4. Mỗi `order_item` phải liên kết đúng `store_order_id`.
5. Trừ tồn kho trong transaction.
6. Sử dụng isolation/concurrency hợp lý để tránh overselling.
7. Lưu snapshot:
   - Product name.
   - SKU code.
   - Unit price.
   - Store name.
   - Shipping service.
8. Clear chỉ các cart item đã checkout thành công.
9. Không hardcode shipping fee bằng 0.
10. Nếu không có dịch vụ giao nhận hợp lệ, block checkout và báo rõ store nào chưa hỗ trợ.

- Seller không được tự sửa shipping fee sau khi customer đã xác nhận.
- Admin có thể can thiệp nhưng phải có audit log.

### 3.7 Đánh giá và bình luận

- Customer chỉ được đánh giá sản phẩm trong store order đã `DELIVERED`.
- Một order item chỉ được đánh giá một lần bởi đúng customer.
- Review có trạng thái moderation.
- Seller chỉ xem review của product thuộc store mình.
- Seller không được xóa review; chỉ có thể phản hồi hoặc báo cáo.
- Admin được ẩn/hiện review vi phạm.
- Có thể thêm `store_review_reply` hoặc seller response nếu đủ thời gian.
- Không render nội dung bình luận bằng raw HTML.

### 3.8 Báo cáo

Admin dashboard:
- Tổng người dùng theo role.
- Tổng stores/carriers theo trạng thái.
- GMV/doanh thu theo ngày/tháng.
- Số đơn và store order theo trạng thái.
- Top product/store.
- Tỷ lệ hủy.
- Thống kê giao nhận.

Seller dashboard:
- Chỉ dữ liệu store của seller.
- Doanh thu, số đơn, top product, low stock, review.
- Lọc theo thời gian.

Carrier dashboard:
- Chỉ dữ liệu provider của carrier.
- Shipment theo trạng thái.
- Phí vận chuyển.
- Tỷ lệ giao thành công.
- Giao trễ.

Không dùng SQL view toàn sàn cho seller nếu view không có StoreId để scope.

### 3.9 Chatbox tư vấn khách hàng — phần nâng cao

Triển khai sau khi các module core đã pass.

Yêu cầu:

- Nút chat nổi, responsive, không che nút checkout.
- Tạo abstraction `IChatAssistantService`.
- Có local fallback không cần API trả lời:
  - Chính sách mua hàng.
  - Trạng thái đơn.
  - Cách tìm sản phẩm.
  - Tìm sản phẩm theo từ khóa, danh mục, khoảng giá.
- Nếu tích hợp AI:
  - API key từ environment/User Secrets.
  - Không hardcode key.
  - Không gửi password, full address, phone hoặc dữ liệu riêng tư không cần thiết.
  - Tool/function gọi catalog phải filter sản phẩm ACTIVE.
  - Khi đọc đơn hàng phải xác thực và chỉ dùng order của customer hiện tại.
  - Có timeout, cancellation token, rate limit và xử lý lỗi.
  - Không cho model tự thay đổi đơn, giá, kho hoặc trạng thái.
- Sanitize input/output.
- Lưu hội thoại tối thiểu hoặc không lưu; nếu lưu phải gắn đúng user/session và có chính sách xóa.
- Chatbox là tính năng bổ sung, không được làm hỏng core marketplace.
